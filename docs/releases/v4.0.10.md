# v4.0.10 Balance Readout and Charge Pipeline Fixes

This release fixes the reported symptom where the balance readout kept showing one
value while the account balance kept falling on a healthy Host. The readout was
rendered from "authoritative snapshot + not-yet-floated debits", and only the
damage-float emitter released those pending debits, so a single failure on the
emission path could pin the number indefinitely without any visible error. The same
failure class also left the charge cursor unadvanced, which made the client replay
the whole ledger every second. Both paths are now decoupled from the visual
pipeline and the emitter recovers on its own.

## 1. Client: the balance readout could stay frozen

`BalanceWidget` kept a `queuedDebit` accumulator and rendered
`snapshot + queuedDebit`. Each debit was added when a charge event was queued and
released when its float was actually emitted, so the readout stayed correct only
while the emitter kept draining. The emitter re-armed itself *after* `emit()` ran,
while `trigger()` only restarted it when `queueTimer.current` was `undefined` and
the queue length was exactly 1. One throw inside the drain timer therefore left
`queueTimer` pointing at an already-fired id with a non-empty queue, and the chain
never restarted: every 60s calibration added back exactly what the account had lost,
so the number held a plausible constant while the balance kept dropping, and the
only trace was an uncaught console error.

The readout is now the authoritative Host snapshot, as the installed build already
did. Debits still drive the per-event decrement animation, but they can no longer
compensate for Host-side spending that the emitter failed to visualise.

## 2. Client: the charge cursor was advanced after the visual work

`chargeSeq.current` was updated at the end of each event's processing, so a throw
anywhere in the float path aborted the loop before the cursor moved. The empty
`catch` around the poll swallowed the error, the cursor stayed at its previous
value, and every following poll re-fetched the entire ledger and re-applied debits
that had already been counted — the readout drifted down until the next calibration
snapped it back. The cursor now advances before the per-event visual work, so a
visual failure can no longer corrupt ledger progress.

## 3. Client: emitter self-recovery and calibration ordering

- The next drain is scheduled in a `finally` block, so a single failed emission no
  longer stops the queue (the error still surfaces on the console).
- `trigger()` starts the drain whenever the queue is non-empty and no timer is
  pending, instead of requiring a queue length of exactly 1.
- The unmount cleanup resets `queueTimer.current` to `undefined` instead of only
  clearing the pending timeout.
- The balance poll applies `lastBalanceSnapshot` and `setDisplay` before the
  recharge animation, so a broken animation cannot skip the calibration and cannot
  turn the card into a query-failure state.

## Verification Scope

Node tests (50/50) and Vitest tests (four package directories) pass,
`tsc --noEmit -p tsconfig.bundle.json` is clean, `scripts/check-standard-bundle.mjs`
reports all checks OK, and `git diff --check` is clean. The bundle check includes
gates that fail when `lib/index.js` and `lib/client.js` are not rebuilt from the
current sources.

The new client tests fail on the previous code with the reported symptom
(`expected 9.51 to be 9.91` for the drifting cursor path and `expected 9.94 to be 9.91`
for the pinned readout) and pass afterwards: the readout tracks the Host balance and
the event cursor walks the ledger once.

Not verified here: a live DSH run. The failure that triggers the emitter stall in a
real browser was not reproduced from the reporter's host, so the fix is verified
against an injected emission fault of the same shape rather than against the
reporter's exact environment.
